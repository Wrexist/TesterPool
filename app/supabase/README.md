# Supabase migrations

The SQL files in `migrations/` are not a hand-maintained approximation of the schema. They are the exact applied history, pulled back out of the live database from `supabase_migrations.schema_migrations`, where Supabase records the statements of every migration it has run. Each file is named for the `version` and `name` of its row, and its contents are the stored statements joined with newlines, byte for byte. Nothing has been reformatted, reordered, or tidied, so the files can be diffed against the table at any time to confirm that disk and database still agree.

Because the filenames carry the timestamp version, filename order is apply order, and it is the only correct order. The migrations are not independent of one another: later ones drop and recreate policies and functions defined by earlier ones, so applying them out of sequence will either fail outright or leave the database in a state that does not match production.

To bring a fresh Supabase project up to this schema, link the project and run `supabase db push` from the directory containing this `supabase/` folder. The CLI compares the local migration files against the remote `schema_migrations` table and applies whatever is missing, in version order. If you are working against a local stack started with `supabase start`, `supabase migration up` does the same thing against the local database. Either way, do not apply the files individually by hand unless you also record them in `schema_migrations` yourself, or the next push will try to run them again.

It is tempting to look at migrations four through six and assume they can be skipped on a new database, since a fresh install has none of the problems they describe. That assumption is wrong. `fix_pgcrypto_search_path`, `harden_rpc_surface`, and `fix_rls_recursion` are corrections to bugs introduced by `core`, `economy`, and `rls_views_seed`, and those bugs are recreated in full every time the first three migrations run. Migration one pins functions to a `search_path` that cannot resolve `pgcrypto`, so signup would fail on the first real user; migration four fixes it. Migration two exposes credit-minting primitives as public RPCs; migration five revokes them. Migration three writes RLS policies that reference each other and cause infinite recursion; migration six moves those lookups into security-definer helpers. A fresh database therefore needs all eleven migrations, applied in order, exactly like an existing one.

One environmental caveat: `jobs_and_notifications` creates the `pg_cron` extension and registers three schedules through `cron.schedule`. Those schedules only exist in a project where `pg_cron` is available and enabled, which on Supabase means a project on a plan and region that offers it. On a local stack or a project without the extension, that migration will fail at the `create extension` line, and the background jobs it defines (pod lifecycle, clock watchdog, nightly maintenance) will not run even if the functions themselves are created. The job functions can always be invoked manually, but nothing will call them on a timer without `pg_cron`.
